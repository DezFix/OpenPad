# OpenPad Virtual Cable — свой драйвер (план, WIP)

> Статус: **проектирование**. Python-часть OpenPad уже умеет работать
> с любым кабелем (VB-Cable) и с запасным режимом Stereo Mix.
> Эта папка — задел под собственный виртуальный драйвер,
> чтобы в будущем было «как у Soundpad»: ставишь OpenPad —
> появляется устройство **OpenPad Virtual Mic**, ничего лишнего.

## Почему это отдельная большая задача

- Виртуальный микрофон в Windows = **kernel-драйвер** (WDM Audio,
  PortCls). User-mode API «создать микрофон из приложения» в Windows
  **нет** — поэтому чисто на Python это сделать невозможно.
- Писать надо на **C++ + WDK** (база — официальный сэмпл Microsoft
  **SysVAD** / старый **MSVAD**: `Microsoft/Windows-driver-samples`,
  папка `audio/sysvad`).
- Главная боль — не код, а **подпись**:
  - при разработке: `bcdedit /set testsigning on` + ребут, на обоях
    надпись «Test Mode», Secure Boot мешает. Только для энтузиастов.
  - для обычных пользователей нужен **релизный подписанный драйвер**:
    attestation-подпись через Microsoft Partner Center. Для этого нужен
    сертификат (исторически EV, ~$200–500/год) + HLK/attestation
    процедура + репутация SmartScreen. Без этого Windows с Secure Boot
    драйвер просто не загрузит.
- Вывод: код драйвера можем вести открыто, тестовые сборки — для
  энтузиастов, а **массовым путём остаются VB-Cable / Stereo Mix**,
  пока у проекта не появится мейнтейнер с сертификатом.
  Референс: `VirtualDrivers/Virtual-Audio-Driver` (MIT, 2025) —
  рабочий открытый драйвер, но тоже **только с включённым test signing**.

## Что задумано (MVP — вариант A: виртуальный микрофон)

Минимальный «OpenPad Cable», без лишнего:

- 1 устройство воспроизведения **OpenPad Speakers** (куда Python-шлёт звук);
- 1 устройство записи **OpenPad Microphone**, отдающее тот же поток
  (+ опционально подмес живого микрофона — позже, сначала без него);
- формат: 48 кГц / 16-bit / stereo (потом расширить);
- установщик: `pnputil /add-driver OpenPadCable.inf /install` от админа;
- имена устройств фиксированные, чтобы Python-часть находила их
  автоматически (как сейчас находит `*cable*`, добавим `*openpad*`).

## Вариант B: инъекция звука прямо в реальный микрофон

Идея: не создавать отдельное устройство, а подмешивать мемы в поток
захвата **существующего** микрофона — тогда в Discord ничего
переключать не надо, все слушают обычный микрофон. Поведение:
«микрофона нет — звука нет, микрофон есть — мемы идут в него».

Технически это делается иначе, чем виртуальный кабель:

- **sAPO** (Software Audio Processing Object) — COM-DLL, которая
  вешается на endpoint реального микрофона и обрабатывает capture-поток.
  Звук из приложения в APO передаётся через shared memory / события,
  APO миксует его в микрофонный сигнал. Примеры: шумодавы, эквалайзеры.
- либо **upper filter driver** на устройство захвата (фильтр поверх
  ksthunk/драйвера микрофона) — ещё ниже уровнем, ещё сложнее.

Почему **не** берём как MVP (честно):

1. Подпись нужна **та же самая** (APO ставится через INF как software
   component, фильтр — kernel). Проблема подписи никуда не девается.
2. Сложнее разработка и отладка: IPC приложение→APO с realtime-миксингом,
   борьба с APO самого вендора (Realtek/MaxxAudio уже вешают свои APO
   на микрофон — конфликты, порядок обработки), разные микрофоны =
   разное поведение. Виртуальный кабель одинаков везде.
3. APO влияет на микрофон **глобально и всегда** (пока висит):
   баг = сломанный микрофон во всех приложениях. У кабеля blast radius
   меньше: не выбрал его в Discord — ничего не поменялось.
4. Нельзя раздельно крутить «громкость мемов» и «громкость голоса»
   средствами Windows-микшера — только своим кодом.
5. Удаление/откат грязнее (чистить регистрацию APO на endpoint'ах).

Итого: вариант B возможен как **фаза 4 (эксперимент)** после того, как
заработает вариант A и появится подписанный релизный канал. Всю
механику микширования (shared-memory ring buffer приложение→драйвер)
проектируем сразу так, чтобы переиспользовать в обоих вариантах.

## Дорожная карта

1. **Фаза 0 (сейчас)**: Python-сторона готова к любому кабелю;
   Stereo Mix — запасной путь без драйвера. ✅ сделано в v0.1+
2. **Фаза 1**: урезать SysVAD до 1 playback + 1 capture loopback,
   переименовать endpoints в OpenPad, собрать в CI (VS2022 + WDK),
   приложить `install.bat`, проверить с `testsigning on`.
   Оценка: 2–6 недель вечерами человеку с опытом WDK.
3. **Фаза 2**: тихий установщик из Python (`Помощь → Установить
   OpenPad Virtual Mic`), авто-выбор устройств, удаление при
   деинсталляции.
4. **Фаза 3**: релизная подпись (сертификат + Partner Center),
   публикация подписанных билдов в Releases. Блокер — деньги/бюрократия,
   а не код.

## Как помочь

- Нужен человек с опытом **WDK / WDM Audio / INF / HLK**.
- Начни с `VirtualDrivers/Virtual-Audio-Driver` и `audio/sysvad`:
  собери их у себя с `testsigning on`, потом приходи с PR сюда.
- Не обещаем сроков: драйвер — отдельный проект внутри OpenPad.

| Путь | Установка | Качество | Статус в OpenPad |
|---|---|---|---|
